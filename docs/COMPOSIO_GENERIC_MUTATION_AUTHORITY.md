# Generic Composio mutation authority

## Decision

The repository requires a `HYBRID_AUTHORITY_MODEL`:

- Existing Gmail draft, Slack alert, Calendar request, and governed GitHub issue features retain their caller-specific durable authority under `0017`.
- The direct generic HTTP mutation surface has no business object, logical ID, or version. If that surface remains a product feature, it needs a shared business-layer generic mutation request created before execution. Until then, generic mutations must fail closed; generic reads may remain available.

The contract is `GENERIC_MUTATION_CONTRACT_READY`: rules and architecture are defined even though caller mapping is incomplete. The ledger sequencing result is `LEDGER_SCHEMA_READY, CALLER_MAPPING_PARTIAL`: the provider action/attempt ledger can be implemented while every authority-missing generic caller stays disabled.

No runtime behavior, schema, migration, or provider lifecycle is implemented here.

## Entry points and caller inventory

Repository-wide tracing found one generic provider-mutation entry path:

`POST /api/composio/execute` → `requestComposioAction` → registry/policy → optional generic approval → `executeComposioAction` → tenant-authoritative account resolution → provider → best-effort logs/timeline/Hermes.

The only other adapter callers are specialized feature routes/services. They are not generic authority merely because they share execution plumbing:

- Gmail draft request: caller-specific ID/version and approval binding (`SPECIALIZED_ALREADY_CLOSED`).
- Slack alert request: caller-specific ID/version and approval binding (`SPECIALIZED_ALREADY_CLOSED`).
- Calendar request/scheduling service: caller-specific ID/version and approval binding (`SPECIALIZED_ALREADY_CLOSED`).
- Governed GitHub issue: stored draft, caller-specific ID/version and approval binding (`SPECIALIZED_ALREADY_CLOSED`).

No background job, cron, workflow, Hermes service, or direct agent independently invokes the generic adapter. Registry permissions for an agent are capability declarations, not evidence that the agent currently calls a mutation.

## Current request and generated IDs

The generic request accepts caller-controlled `agentId`, `tool`, `action`, opaque `inputParams`, optional `entityId`, confidence, risk level, recipient email, and notes. Organization is resolved from authenticated server context. It accepts no logical action ID, version, connected-account ID, business request ID, workflow ID, or immutable authority descriptor.

Generated identifiers are not business identity:

| ID | Classification | Reason |
|---|---|---|
| adapter `logId` UUID | ATTEMPT_ID | generated at adapter boundary; changes on retry |
| generic approval UUID | GOVERNANCE_ID | optional and policy-generated, not universal recurrence identity |
| Composio action-log UUID | OBSERVABILITY_ID | generated by logging, including after provider call |
| timeline row ID/default | OBSERVABILITY_ID | execution history, not caller intent |
| Hermes event UUID | OBSERVABILITY_ID | emitted after outcome/approval processing |
| provider execution/callback/receipt | PROVIDER_RECEIPT | exists during/after invocation |
| caller `entityId` | NOT_ELIGIBLE | optional provider entity selector verified against resolved account |

An HTTP request is ephemeral. Approval is governance evidence, not business identity: auto-executable mutations may have none, retries or approval regeneration may create another, and approval generations do not define independent business recurrence.

## Logical identity and versions

Canonical identity remains:

`org_id + normalized_toolkit + logical_provider_action_id + provider_action_version`

A generic logical ID is explicit, nonblank, caller/business-owned, created before invocation, tenant-scoped through canonical identity, stable across retries, exactly one intended provider-side business action, and distinct for later independent operations. It is never an executor UUID, timestamp/bucket, receipt, log ID, argument hash, target resource, `entityId`, or approval ID by default.

Version is the integrated positive safe-integer model: initially 1 where appropriate, stable across retry, incremented for a material pre-success authority revision, and never an attempt, approval generation, recurrence counter, timestamp, hash, or receipt. Current V2 rejects requested V1 before provider invocation. Success and uncertainty cannot be escaped with a version bump.

Provider resource keys—recipient/thread, channel, calendar event, spreadsheet/range, repository/issue, or Stripe object—belong in immutable authority descriptors; they are not automatically business identity. Two independent actions may target the same resource.

Toolkit is already canonical identity. Provider action and connected account are bound authority. The server must reject an action that is not registered to the claimed canonical toolkit. Same ID/version with changed toolkit, action, or account is an authority mismatch. An intentional material revision requires renewed authority and usually a later version; a changed business purpose requires a new logical ID.

## Action-specific authority

There is no safe universal provider payload schema. Each business caller owns an immutable action-specific descriptor containing every material argument, target, action, account authority reference, and approval scope it actually uses. The shared execution layer may validate that a descriptor and version exist, but cannot infer their business meaning or generate them.

Retry preserves ID/version. Confirmed retryable failure permits a separately authorized new attempt under the same identity/version. Invocation-in-progress, provider-accepted, or uncertain blocks blind retry. Confirmed success exhausts the business action family; later independent work requires a new logical ID.

## Business objects and multi-action boundaries

The generic HTTP caller has no durable pre-provider object. Specialized request IDs qualify only for their one governed action. A workflow/job/recommendation ID would be `TOO_BROAD` whenever it can emit multiple provider mutations; it would require a durable business action child owned upstream. Concatenating a job ID and tool name in provider plumbing is not a substitute.

No current direct-agent, Hermes, or workflow generic mutation object is available to classify. Agent name and conversation ID are not identity. Historical action logs, timeline rows, approvals, and Hermes events are `HISTORICAL_OBSERVABILITY_ONLY`; identities/versions must not be fabricated retroactively.

## Architecture ownership

### Caller-specific business authority

Best for features already possessing a semantically precise request row. That row owns business request ID, tenant, action/intent, immutable payload revisions, provider-action version, account authority reference, business approval/cancellation/revision state.

### Shared generic mutation request

Required only if direct generic mutation remains a supported feature. The route may become the intentional business-request creation boundary, persisting tenant, toolkit/action, account reference, immutable payload, logical ID/version, business approval, cancellation, and revision state before any provider call. It must not immediately execute an arbitrary mutation without that persisted authority.

### Provider action/attempt ledger

Exclusively owns canonical claims, attempt authorization/history, invocation-in-progress, provider acceptance, confirmed provider outcomes, uncertainty, receipts, reconciliation, and retry gating. Neither shared nor caller-specific business requests duplicate this lifecycle; outcome fields there are projections only.

## Direct route policy and eligibility

Future policy is `DISABLE_GENERIC_MUTATIONS_WITHOUT_AUTHORITY`. Reads remain available through server classification and tenant-authorized account resolution. A mutation may proceed only by referencing a persisted caller-specific or shared generic business request with trusted organization, canonical toolkit, a mutation registered to that toolkit, durable logical ID, explicitly supplied positive requested and current versions that are equal, complete immutable descriptor, authorized account, valid approval when required, and a successful future ledger claim. Missing current version is an authority failure. Client input cannot label a mutation as read.

The provider ledger consumes already-validated caller authority; it does not create it. It must not generate logical IDs or versions, infer current version or toolkit/action compatibility from caller claims, infer business identity from provider arguments, or synthesize authority from caller type.

No-human-approval does not waive identity, version, account, payload, action claim, or attempt lifecycle. Approval-governed mutations additionally bind organization, ID/version, toolkit/action, account, immutable descriptor, and approving principal; approval never replaces business identity.

## Current risks and readiness

The current generic path has no durable claim before provider invocation. Equivalent concurrent auto-executable requests can invoke a fake provider twice. Generic approval may reduce immediacy but does not provide canonical deduplication. Provider execution occurs before best-effort action-log/timeline/Hermes persistence, so provider success plus local failure cannot be reliably distinguished from uncertainty.

| Caller/feature | Toolkit/actions | Durable business object | Logical ID | Version | Approval | Status |
|---|---|---|---|---|---|---|
| Generic HTTP route | all 14 mutations | none | MISSING | MISSING | policy-dependent | MISSING |
| Specialized Gmail draft | Gmail create draft | request row | READY | READY | bound | SPECIALIZED_ALREADY_CLOSED |
| Specialized Slack alert | Slack send message | request row | READY | READY | bound | SPECIALIZED_ALREADY_CLOSED |
| Specialized Calendar | Calendar create/update/delete | request row | READY | READY | bound | SPECIALIZED_ALREADY_CLOSED |
| Governed GitHub issue | GitHub create issue | improvement task + stored draft | READY | READY | bound | SPECIALIZED_ALREADY_CLOSED |

Every registered mutation remains blocked through the generic route in future canonical mode. Actions also having specialized coverage must use that governed path; Gmail reply, Slack channel/invite, and all Sheets mutations need a new business authority owner before execution.

No migration is added. A shared generic business request may consume `0018`; numbering follows dependency order. The provider ledger may nevertheless be implemented next while generic authority-missing callers remain disabled.

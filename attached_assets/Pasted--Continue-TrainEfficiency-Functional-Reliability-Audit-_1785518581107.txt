# Continue TrainEfficiency Functional Reliability Audit

The first reliability pass found and fixed several important failures:

1. Attendance Tracker saves returned 401 because ten API calls used raw `fetch()` rather than `authenticatedFetch`.
2. Nine Hermes routes checked `req.user` without first running `isAuthenticated`.
3. Twelve AgentMail call sites attempted to read `req.user.orgId`, which Replit authentication does not provide, instead of using `resolveOrgIdOrThrow`.
4. The reliability monitor probed an obsolete API route.
5. Workout Builder mutations failed to invalidate the program-library bootstrap query.
6. The athletic-program sidebar query did not check `response.ok`.

These findings demonstrate recurring systemic patterns.

Do not treat the audit as complete.

Continue through the entire repository and eliminate every remaining instance of these failure classes before moving to cosmetic work.

## Immediate instruction

Implement the proposed follow-up tasks numbered 13–15 rather than merely documenting them, unless one requires an external credential or a product decision that cannot be inferred safely.

Then continue with the systematic audit below.

---

# 1. Raw Fetch Authentication Audit

Search all production frontend code for:

```ts
fetch(
window.fetch(
globalThis.fetch(
```

Classify every occurrence.

For calls to authenticated TrainEfficiency API routes:

* Replace raw `fetch()` with the project’s canonical `authenticatedFetch`.
* Preserve request headers and body behavior.
* Ensure JSON content headers are set where required.
* Check `response.ok`.
* Parse and surface the server error safely.
* Do not show success until the server confirms persistence.
* Prevent duplicate submissions.

Raw `fetch()` may remain only when justified, such as:

* Public unauthenticated endpoints.
* Signed external URLs.
* File or blob retrieval requiring different behavior.
* Third-party services intentionally called from the browser.

Document every retained raw `fetch()` and why it is safe.

Pay particular attention to:

* Settings pages.
* Configuration editors.
* Dialog-based mutations.
* Sidebar queries.
* Dashboard widgets.
* Test-send buttons.
* Approval actions.
* Admin screens.
* Legacy components.
* Mobile-specific components.

---

# 2. Authentication Middleware Audit

Search all server routes for handlers that use:

```ts
req.user
req.isAuthenticated()
req.user?.claims
req.user?.id
```

Verify that each protected route executes the canonical `isAuthenticated` middleware before reading authenticated identity.

Find routes with custom guards such as:

* `requireAdmin`
* `requireOwner`
* `requireCoach`
* `requireStaff`
* `requireOrg`
* inline role checks

Confirm those guards run only after authentication has populated the request.

Fix middleware ordering rather than duplicating token parsing.

Test:

* No token.
* Valid token.
* Expired or invalid token.
* Authenticated but unauthorized role.
* Correct authorized role.

Responses must distinguish appropriately between:

* `401 Unauthorized`
* `403 Forbidden`

---

# 3. Canonical Organization Resolution Audit

Search for all code that trusts organization context from:

```ts
req.body.orgId
req.body.organizationId
req.query.orgId
req.query.organizationId
req.params.orgId
req.params.organizationId
req.user?.orgId
req.user?.organizationId
```

For normal organization-user routes:

* Resolve organization membership using the canonical server-side resolver.
* Use `resolveOrgIdOrThrow` or the established equivalent.
* Do not trust organization identity supplied by the browser.
* Validate entity ownership after resolving the organization.
* Reject cross-organization access.

Explicit organization IDs may remain only for legitimate platform-admin or signed internal-service endpoints with a documented trust boundary.

Produce a list of those exceptions.

Test two organizations against every repaired route.

---

# 4. Response Handling Audit

Search frontend code for API operations that:

* Call `.json()` without checking `response.ok`.
* Ignore non-2xx responses.
* Use empty `catch` blocks.
* Only call `console.error`.
* Return an empty array after an API failure.
* Display a success toast before awaiting the mutation.
* Optimistically mutate without rollback.
* Swallow JSON parse errors.
* Assume every error response contains JSON.

Create or reuse a shared safe response helper where appropriate.

Every user-facing failure should produce a useful message without crashing the page.

Do not conceal authorization, validation, or persistence failures as empty states.

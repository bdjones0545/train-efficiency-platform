We are beginning the production integration between TrainEfficiency and our always-on virtual computer, Kevin.

Kevin is already reachable through a Cloudflare Tunnel and will serve as the AI control plane for TrainEfficiency’s specialized agents.

Do not move TrainEfficiency, its database, authentication, business logic, or frontend onto the virtual computer.

The architecture must remain:

TrainEfficiency frontend
→ TrainEfficiency backend
→ signed request through Cloudflare Tunnel
→ Kevin agent gateway
→ specialized Hermes agent
→ signed callback
→ TrainEfficiency database and UI

TrainEfficiency remains the system of record.

Kevin owns agent execution, identities, skills, memory, tool use, orchestration, retries, and health monitoring.

## Objective

Build the foundational agent-integration layer inside TrainEfficiency.

For this phase, implement one complete production-style vertical slice using the Retention Agent.

The first workflow will be:

1. An authorized TrainEfficiency user clicks “Analyze Retention Risk.”
2. TrainEfficiency creates an internal agent job.
3. The TrainEfficiency backend sends a signed asynchronous task request to Kevin.
4. Kevin accepts the request and returns a task ID.
5. Kevin later sends a signed callback containing the result.
6. TrainEfficiency validates the callback.
7. TrainEfficiency stores the result.
8. The UI displays the Retention Agent’s findings and recommendations.

Do not connect the browser directly to Kevin.

All Kevin traffic must pass through the TrainEfficiency backend.

## 5. Internal API to Start an Analysis

Create a backend endpoint similar to:

```text

```

Requirements:

* Require authentication.
* Require the user to belong to the organization.
* Require an authorized role.
* Confirm that the client belongs to the same organization.
* Validate that the Retention Agent is enabled.
* Create the agent job before dispatching.
* Generate an idempotency key.
* Generate a correlation ID.

## 7. Outbound HMAC Signing

Sign every outbound request to Kevin.

Use headers similar to:

```text
X-TE-Timestamp
X-TE-Request-ID
X-TE-Correlation-ID
X-TE-Idempotency-Key
X-TE-Body-SHA256
X-TE-Signature
```

The signature should cover a canonical representation of:

```text
HTTP method
request path
timestamp
request ID
body hash
```

Requirements:

* Use SHA-256.
* Use constant-time comparison where verification is performed.
* Use exact raw request bytes or deterministic canonical serialization.
* Prevent accidental signature differences caused by JSON key ordering.
* Do not log the HMAC secret or full signature.
* Add structured logs for dispatch success and failure.

Create reusable signing utilities rather than placing HMAC logic directly inside the route.

## 9. Callback Endpoint

Create:

```text
POST /api/agent-callbacks/kevin
```

This endpoint must:

* Be server-to-server only.
* Read the raw request body.
* Validate the callback HMAC.
* Validate the timestamp.
* Reject requests outside the allowed time window.
* Validate the callback schema.
* Confirm the local job exists.
* Match the organization, agent, task type, correlation ID, and remote task ID.
* Be idempotent.
* Reject mismatched or replayed callbacks.
* Persist results transactionally.
* Update the job status.
* Return a stable acknowledgment response.

Suggested callback body:

```json
{
  "schemaVersion": "1.0",
  "taskId": "local-agent-job-uuid",
  "remoteTaskId": "kevin-task-uuid",
  "agentId": "retention-agent",
  "taskType": "evaluate_client_retention_risk",
  "organizationId": "uuid",
  "correlationId": "uuid",
  "status": "completed",
  "completedAt": "ISO-8601",
  "result": {
    "clientId": "uuid",
    "riskLevel": "high",
    "riskScore": 82,
    "confidenceScore": 88,
    "summary": "Attendance and engagement have declined.",
    "riskFactors": [],
    "recommendedActions": [],
    "draftMessage": "Optional draft message",
    "evidence": [],
    "modelVersion": "retention-agent-1.0.0"
  }
}
```

The callback must support at minimum:

```text
running
requires_approval
completed
failed
blocked_by_policy
cancelled
```

For failed callbacks, require a safe structured error object.

## 10. Callback Persistence

For a completed Retention Agent task, persist the result and update the agent job in one database transaction.

The transaction should:

1. Lock or safely select the agent job.
2. Confirm the callback has not already been processed.
3. Validate all identifiers.
4. Insert or update the retention analysis.
5. Mark the agent job completed.
6. Save the structured result payload.
7. Set `completed_at`.
8. Write an audit event.
9. Commit atomically.

A callback must never create a completed analysis while leaving the job in a failed or running state.

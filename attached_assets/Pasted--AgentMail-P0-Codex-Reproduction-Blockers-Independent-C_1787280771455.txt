## 1. Fix Migration Transaction Boundary

Current defect:

`pg_advisory_xact_lock` is acquired through a transaction, but some required DDL subsequently runs through the global connection/pool via `execDDL`.

The global connection cannot see tables created but not yet committed inside the transaction.

Codex reproduced:

`42P01: relation "agent_mail_inbound_messages" does not exist`

### Required fix

Every AgentMail DDL operation governed by this migration must execute through the SAME locked transaction/connection.

Do not call the global DB/pool from inside the locked migration.

Preferred structure:

`db.transaction(async tx => {`
`  acquire advisory xact lock through tx`
`  execute ALL AgentMail DDL through tx`
`})`

Refactor `execDDL` if necessary so it accepts an executor/transaction rather than reaching for the global pool.

### Prove behaviorally

Against a completely fresh disposable PostgreSQL database:

* one migration succeeds
* serial rerun succeeds
* two concurrent migration callers succeed
* all expected tables exist
* all expected columns exist
* all expected indexes/constraints exist
* `_ready` becomes true only after complete success

Force one required DDL statement to fail and prove:

* transaction rolls back
* `_ready` remains false
* webhook returns 503
* partial schema is not treated as ready

Do not accept source-string inspection for this gate.

## 2. Fix Effect Ledger Semantics

Current critical defect:

`tryEffect()` inserts the unique effect-log record BEFORE executing the business effect.

If the business write fails, the ledger remains and retry permanently skips the unfinished effect.

The ledger currently means:

`claimed`

while the code treats it as:

`completed`.

### Required invariant

An effect may be considered complete only AFTER its business write succeeds.

Implement a proper minimal state model.

For example:

`pending`
→ business operation
→ `completed`

On failure:

→ `failed` or retryable state

The exact schema is your choice, but it must guarantee:

* concurrent workers cannot execute the same effect simultaneously
* successful effect is not repeated
* failed effect remains retryable
* crash after claim but before completion is reclaimable
* ledger cannot say completed when the business write did not happen

A transaction combining ledger and business write is preferred where both use the same database and transactional boundary.

Where that is impossible, implement explicit claim/lease/completion semantics.

### Remove swallowed downstream failures

Review all six effects:

* prospect
* applicant
* software_task
* attention_item
* reply_queue
* ceo_timeline

Codex found some helpers catch/suppress errors or return `null`.

A failed business write must not be recorded as completed.

Distinguish intentionally skipped/no-op from actual success.

## 4. Strict Svix Timestamp Parsing

Current defect:

Values such as:

`1724200000junk`

are accepted by `parseInt()`.

Require the entire timestamp value to be a valid integer representation.

Reject:

* suffix junk
* prefix junk
* decimals
* whitespace tricks if not explicitly allowed by provider contract
* empty value
* overflow/invalid numeric range

Do not merely parse the numeric prefix.

Add signed malformed-timestamp tests.

## 5. Svix Delivery Replay Protection

Cryptographic timestamp tolerance alone does not prevent replay of the exact same valid delivery during the tolerance window.

Add a bounded replay ledger keyed by the provider delivery identity, preferably:

`svix-id`

Requirements:

* first valid delivery accepted
* exact same delivery ID replay rejected/ignored safely
* ledger written only after authentication succeeds
* retention bounded appropriately
* concurrent duplicate delivery cannot both process

Coordinate this with existing provider-message idempotency rather than creating contradictory duplicate semantics.
